## Correction and independent limits

- `PiOwnerClient.call` now uses `json.dumps(..., ensure_ascii=False)` and explicit
  UTF-8 encoding. The actual encoded **whole request including newline** must be
  at most65536 bytes, checked before creating a pending request or writing.
- GTK checks the owner's16000 **UTF-16 code-unit** limit (JS `text.length`), not
  Python/GLib Unicode-codepoint count, and the UTF-8 JSON byte budget **before
  clearing the composer**. It counts JSON escapes plus the actual client's69-byte
  chat envelope: default Python JSON separators, fixed32-character UUID hex ID,
  op/text fields and newline. The separate GTK→adapter frame is generated by the
  same encoder used for submission and checked too. No extra owner fields or
  advisory routing are added by this text path.
- The adapter's length validation uses UTF-16 units as well. For example11000
  Chinese characters use11000 units and33000 raw UTF-8 bytes;8000 supplementary
  scalars use16000 units and32000 bytes, while8001 use16002 units and are refused.
  **16000 Python Unicode codepoints is not the owner's contract.** Escaped
  controls can also exceed the frame budget below the unit limit; neither limit
  substitutes for the other. Whitespace-only drafts are rejected before clearing.
- Rejected native drafts remain in the actual `GtkTextBuffer`. Attachment sends
  still use the existing legacy route, not the Pi text preflight; no attachment
  removal/payload/media-route or appearance change was made.
